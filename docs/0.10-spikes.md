# 0.10 — wyniki sprawdzeń (2026-09-27)

opencode 1.18.25 (npm, `opencode-ai`), t3code z `main` (pingdotgg/t3code, sklonowany tylko do czytania). Nic nie było uruchamiane na koncie użytkownika i nie zmieniano jego konfiguracji.

## S1: zdarzenia pluginu opencode

- Plugin to moduł JS/TS w `~/.config/opencode/plugin/` (globalnie) albo `.opencode/plugin/` (projekt). Eksportuje funkcję `async (input) => hooks`; `input` ma `directory`, `worktree`, `project`, `client`, `serverUrl`.
- Hooki: `event({ event })` (wszystkie zdarzenia szyny), `chat.message` (`input.model = { providerID, modelID }`, `input.sessionID`), `tool.execute.before/after` (`tool`, `sessionID`, `callID`), `permission.ask`.
- Nazwy zdarzeń w binarce 1.18.25 (lokalne typy `@opencode-ai/sdk` 1.14.20 są starsze i ich nie mają): `session.status` (`status.type`: `busy`, `idle`, `retry`), `session.created`, `session.updated`, `session.deleted`, `session.error`, `permission.asked`, `permission.replied`, `question.asked`, `question.replied`, `question.rejected`, `todo.updated`, `message.part.updated` (część `tool` z `state.status`: `pending`, `running`, `completed`, `error`). `session.idle` i `permission.updated` ze starszych typów w 1.18 nie występują; `session.status` z `idle` je zastępuje.
- Mapa stanów: `busy` → `working` (z narzędziem z `tool.execute.before`), `retry` → `working`, `idle` → `done`, `permission.asked`/`question.asked` → `needs_you` (tytuł zgody albo pytania jako tekst), `*.replied`/`*.rejected` → powrót do `working`, `session.error` → `error`, `session.deleted` → `ended`.
- Plugin działa w procesie opencode: `process.pid` to PID agenta, `process.ppid` prowadzi do programu (terminal, t3code, aplikacja opencode).
- Wysyłka: `fetch` na `http://127.0.0.1:<port>/v1/events/opencode` z tokenem z `~/.agent-pets/endpoint.json`, czytanym przy każdym zdarzeniu (widżet mógł się zrestartować), z limitem 300 ms i bez wyjątków na zewnątrz — plugin nigdy nie przeszkadza opencode.
- Nazwy narzędzi (z dokumentacji opencode; w binarce nie dało się ich jednoznacznie wyłuskać): `bash`, `edit`, `write`, `patch`, `read`, `grep`, `glob`, `list`, `webfetch`, `task` (subagent), `todowrite`. Mapowanie na `Tool` po wzorcach, nieznane → `other`, więc nowa nazwa niczego nie psuje.
- **Do potwierdzenia na żywo przy teście 0.10:** kształt `properties` w 1.18, czy `question.asked` ma tekst pytania, nazwy narzędzi. Pierwsza sesja użytkownika z włączonym pluginem, z zapisem fixtures bez treści.

## S2: t3code

- **Claude:** `@anthropic-ai/claude-agent-sdk` z `settingSources: ["user", "project", …]` (`ClaudeAdapter.ts`), więc hooki z `~/.claude/settings.json` się odpalają i sesja trafia do nas jak każda inna. Zapas z czytania transkryptu niepotrzebny.
- **Codex:** app-server z `clientInfo.name = "t3code_desktop"` — to trafia do `session_meta.originator`. Dziś nieznany `originator` daje `CodexApp` (zły podpis i zły skok); nowa mapa: `t3code_desktop` → `T3code`.
- **Antigravity, Cursor, Grok:** przez ACP (`agy`, `cursor-agent`, `grok`); ich własne hooki działają jak przy uruchomieniu z terminala. **opencode:** przez własny serwer opencode, więc plugin też działa.

## S3: drzewo procesów

- Łańcuch tej sesji: `pwsh.exe ← cmd.exe ← claude.exe ← claude.exe ← explorer.exe`. Aplikacja Claude Desktop i CLI Claude Code mają tę samą nazwę `claude.exe`, więc program rozpoznajemy po liście znanych gospodarzy, nie „pierwszy proces inny niż agent”; Claude Desktop dalej rozstrzyga `entrypoint` z rejestru sesji (jak dziś).
- `pid::process_entry` robi osobny zrzut procesów na każdy krok. Przejście po 8 poziomach to 8 zrzutów; zamiast tego jeden zrzut Toolhelp i mapa `pid → (rodzic, nazwa)` (344 procesy u użytkownika). WMI (`Win32_Process`) jest za wolne (137 ms) i nie wchodzi w grę w hooku.
- Zakończony rodzic i ponownie użyty PID: rodzic musi mieć czas utworzenia wcześniejszy niż dziecko (`GetProcessTimes`), inaczej przerywamy wędrówkę.
